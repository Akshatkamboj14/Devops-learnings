# Docker Notes - Core Concepts and Commands

## Installation and Basic Checks

1.  **To install Docker**:
    sudo apt-get update -y
    sudo apt-get install -y docker.io

    (Note: For more robust installation, consider using Docker's official repository for `docker-ce` as discussed previously.)

2.  **To check if Docker is installed and running**:
    sudo systemctl status docker

    This will show if the Docker daemon is `active (running)`.
    Or, a quick test:
    docker run hello-world

    This command will pull the `hello-world` image (if not present) and run it, showing a "Hello from Docker\!" message if successful.

3.  **To login to Docker Hub**:
    docker login -u akshat1414

    After running this, instead of your password, provide your **Personal Access Token (PAT)** for security.

4.  **Command for pulling/running a MySQL image**:
    docker run -e MYSQL\_ROOT\_PASSWORD=root mysql

    This command pulls the `mysql:latest` image and runs it, setting the root password. Note: For persistent data, you'd use a volume.

5.  **To stop/start a container**:
    docker stop \<container-id-or-name\>
    docker start \<container-id-or-name\>

6.  **To run an image in the background (detached mode)**:
    docker run -d -e MYSQL\_ROOT\_PASSWORD=root mysql

    The `-d` flag means "detach mode," allowing the container to run in the background without tying up your terminal.

7.  **Docker Workflow**:
    Dockerfile -\> Image -\> Container
    A `Dockerfile` is a blueprint to build an `Image`, and an `Image` is used to create a runnable `Container`.

8.  **Example of a Dockerfile (Java Application)**:

    # pull a base image which gives all required tools and libraries

    FROM openjdk:17-jdk-alpine

    # create a folder where the app code will be stored

    WORKDIR /app

    # Copy the source code from your HOST MACHINE to your container

    COPY src/Main.java /app/Main.java

    # compilation

    RUN javac Main.java

    # running the application

    CMD ["java", "Main"]

9.  **To build an image from a Dockerfile**:
    docker build -t java-app .

    The `-t` flag gives a name (`java-app`) and optionally a tag (e.g., `java-app:1.0`) to the image. The `.` indicates the build context (current directory).

10. **To create and run a container from an image**:
    docker run java-app

11. **To publish or connect the container port and the host machine port**:
    docker run -d -p \<Host-machine-port\>:\<container-port\> \<image-name\>

    For example, `docker run -d -p 80:80 flask-app` maps host port 80 to container port 80.

12. **To check logs of a container**:
    docker logs \<container-id-or-name\>

13. **To attach to a running container's standard I/O**:
    docker attach \<container-id-or-name\>

14. **To make a container interactive (execute commands inside it)**:
    docker exec -it \<container-id-or-name\> bash

    The `-it` flags provide an interactive terminal. This is useful for debugging or running specific commands inside a running container (e.g., `mysql` client inside a MySQL container).

15. **Main types of networks in Docker**:

    1.  Host: Container shares the host's network stack directly (no isolation).
    2.  Bridge (default): Containers on the same bridge network can communicate; isolated from other bridge networks.
    3.  User-defined Bridge (Custom): A bridge network you create, offering better isolation and DNS resolution between containers.
    4.  None: No network interface inside the container.

16. **To list all Docker networks**:
    docker network ls

17. **To create a user-defined bridge network**:
    docker network create my-network -d bridge

## Docker Volumes and Storage

18. **Docker Volumes (for Persistent Data)**:

      * **Concept**: Volumes are the preferred mechanism for persisting data generated by Docker containers. Unlike data stored within a container's writable layer (which is ephemeral and lost when the container is removed), volumes are managed by Docker and exist independently on the host machine.

      * **Purpose**: Essential for stateful applications like databases, where data must survive container restarts, upgrades, or deletions.

      * **Basic Commands**:

          * **Create a named volume**:
            docker volume create my-data-volume

          * **List all volumes**:
            docker volume ls

          * **Inspect a volume**:
            docker volume inspect my-data-volume

          * **Remove a volume**:
            docker volume rm my-data-volume

            (Note: A volume can only be removed if it's not in use by any container.)

          * **Run a container with a named volume**:
            docker run -d -v my-data-volume:/path/in/container \<image-name\>

            Example for MySQL with persistent data:
            docker run -d  
            \-e MYSQL\_ROOT\_PASSWORD=root  
            \-v mysql-data:/var/lib/mysql  
            \--name my-persistent-mysql  
            mysql

            Here, `mysql-data` is the named volume, and `/var/lib/mysql` is where MySQL stores its data inside the container.

## Docker Compose

19. **Docker Compose**:

      * **Concept**: A tool for defining and running multi-container Docker applications. Instead of running multiple `docker run` commands for each service (e.g., database, backend API, frontend), you define all your services, networks, and volumes in a single YAML file (`docker-compose.yml`).

      * **Purpose**: Simplifies the orchestration of complex, multi-service applications during development, testing, and sometimes even in production (for simpler setups). It allows you to manage your entire application stack with a few commands.

      * **Basic `docker-compose.yml` Structure**:

        # docker-compose.yml

        version: '3.8' \# Specify Compose file format version

        services:
        web: \# Service name (e.g., your Flask app)
        build: . \# Build from Dockerfile in current directory
        ports:
        \- "80:5000"
        environment:
        \- DATABASE\_URL=postgres://user:password@db:5432/mydb
        depends\_on: \# Defines dependency on other services
        \- db
        db: \# Service name (e.g., PostgreSQL database)
        image: postgres:15.1-alpine
        environment:
        \- POSTGRES\_PASSWORD=foobarbaz
        \- POSTGRES\_DB=mydb
        volumes:
        \- pgdata:/var/lib/postgresql/data \# Use a named volume for persistence

        volumes: \# Define named volumes used by services
        pgdata:

      * **Basic Commands**:

          * **Start all services defined in `docker-compose.yml`**:
            docker compose up -d

            The `-d` runs services in detached mode. If you omit `-d`, logs will stream to your terminal.

          * **Stop and remove all services, networks, and volumes defined in `docker-compose.yml`**:
            docker compose down

            (Use `docker compose down --volumes` to also remove named volumes.)

          * **Build images defined in `docker-compose.yml`**:
            docker compose build

          * **View running services**:
            docker compose ps

## Multi-Stage Docker Build

20. **Multi-Stage Docker Build**:

      * **Concept**: A feature in Dockerfiles that allows you to use multiple `FROM` statements. Each `FROM` instruction starts a new build stage. You can then selectively copy artifacts (like compiled binaries or build outputs) from one stage to a final, much smaller image in a subsequent stage.

      * **Purpose**: Primarily used to **reduce the final Docker image size** and improve security.

          * **Smaller Images**: Avoids including unnecessary build tools, SDKs, and temporary files in the final production image. For example, you don't need a Java compiler (JDK) in your final image if you only need the Java Runtime (JRE) to run the compiled `.class` files.

          * **Improved Security**: Less attack surface in smaller images.

          * **Cleaner Builds**: Separates the build environment from the runtime environment.

      * **Example of a Multi-Stage Dockerfile (Java Application)**:

        # \--- Stage 1: Build Stage ---

        FROM openjdk:17-jdk-alpine AS builder \# Name this stage 'builder'

        WORKDIR /app

        COPY src/Main.java /app/Main.java

        RUN javac Main.java \# Compile the Java code

        # \--- Stage 2: Runtime Stage ---

        FROM openjdk:17-jre-alpine \# Use a smaller JRE-only image for runtime

        WORKDIR /app

        # Copy only the compiled artifact from the 'builder' stage

        COPY --from=builder /app/Main.class /app/Main.class

        # Running the application

        CMD ["java", "Main"]

          * **Explanation**:

              * The first `FROM` (line 2) starts the `builder` stage, which includes the full JDK for compilation.

              * The second `FROM` (line 11) starts a new, separate stage using only the JRE.

              * `COPY --from=builder /app/Main.class /app/Main.class` (line 15) is the key. It copies *only* the compiled `Main.class` file from the `builder` stage into the much smaller `openjdk:17-jre-alpine` image. The `javac` compiler and other build tools from the `builder` stage are discarded, resulting in a significantly smaller final image.
