Essential Git Commands
Basic Git Workflow Commands
* git init
   * Meaning: Initializes a new Git repository in the current directory. When executed, Git creates a hidden .git/ subdirectory. This special directory is where Git stores all the necessary metadata for your project, including object databases (commits, trees, blobs), references (branches, tags), and configuration files. It's the brain of your repository, allowing Git to track every change.
* git status
   * Meaning: Shows the current state of your working directory and staging area. It provides crucial feedback on which files have been modified since the last commit, which new files are untracked, and which changes are currently staged and ready for the next commit. This command is your constant companion for understanding what Git sees.
   * Example Output:
      * Untracked files: (usually red): New files Git hasn't seen before.
      * Changes not staged for commit: (usually red): Files Git knows about, but their recent modifications haven't been added to the staging area.
      * Changes to be committed: (usually green): Files whose changes are in the staging area, ready for the next commit.
* git add <file>
   * Meaning: Adds changes from a specific file in your working directory to the staging area. This is the first step in preparing a snapshot. Git records the current state of the specified file(s) for the upcoming commit.
* git add .
   * Meaning: A convenient shorthand to add all new and modified files (and their changes) in the current directory and its subdirectories to the staging area. Be cautious with git add . as it stages everything, so always run git status first to review what will be added.
* git commit -m "Your message"
   * Meaning: Saves the staged changes as a new snapshot (a "commit") in the repository's history. Each commit represents a point in time in your project's development. The -m flag is used to provide a concise, descriptive commit message directly on the command line. A good commit message explains why the changes were made, not just what was changed, making your project history understandable for yourself and collaborators.
* git log
   * Meaning: Displays the chronological commit history of the current branch. For each commit, it shows the unique commit hash (SHA-1), author, date, and the commit message. Useful flags include --oneline (for a concise one-line summary per commit) and --graph (to visualize the branching and merging history).
Remote Repository Commands
* git clone <repository_url>
   * Meaning: Downloads an existing Git repository from a remote server (like GitHub, GitLab, or Bitbucket) to your local machine. This command not only copies all the files but also the entire commit history, branches, and sets up a default remote named origin pointing back to the source repository.
* git remote add <name> <URL>
   * Meaning: Links your local repository to a new remote one. While origin is the conventional name for the primary remote, you might add other remotes (e.g., upstream for the original project you forked from) to manage multiple sources of changes.
* git push <remote> <branch>
   * Meaning: Uploads your local commits from the specified local branch to the corresponding branch on the remote repository. This makes your local changes visible and available to other collaborators.
   * Example: git push origin main sends your local main branch's new commits to the main branch on the origin remote.
   * First time push: When pushing a local branch for the first time, using git push -u origin main (or -u with your branch name) is common. The -u (or --set-upstream) flag establishes a tracking relationship between your local branch and the remote branch. After this, future pushes and pulls for that branch can often be simplified to just git push or git pull. Authentication (e.g., via SSH keys or Personal Access Tokens for HTTPS) is required for this operation.
* git fetch <remote>
   * Meaning: Downloads new commits, branches, and tags from the specified remote repository to your local repository. Crucially, it does NOT automatically merge these changes into your current local working branch. Instead, it updates your "remote-tracking branches" (e.g., origin/main, origin/feature-x), which are local copies of the remote branches.
   * Purpose: git fetch allows you to see what changes have happened on the remote without immediately integrating them into your active work. This is useful for reviewing others' progress, checking for potential conflicts, or updating your local view of the remote without disrupting your current development.
* git pull <remote> <branch>
   * Meaning: A convenience command that is essentially a combination of two distinct operations:
      1. git fetch <remote>: First, it downloads all new changes from the specified remote.
      2. git merge <remote>/<branch>: Second, it immediately merges the downloaded changes from the remote-tracking branch (e.g., origin/main) into your current local branch.
   * Purpose: To synchronize your current local branch with its remote counterpart, both downloading and integrating changes in one step. If an upstream tracking relationship has been set up (e.g., with git push -u), you can often simply run git pull without specifying the remote and branch.
Branching and Navigation Commands
* git branch
   * Meaning: Lists all local branches in your repository. The current branch you are on will be highlighted, usually with an asterisk (*) next to its name. This helps you quickly identify your active line of development.
* git branch <new-branch-name>
   * Meaning: Creates a new local branch with the specified name. This command simply creates the new pointer; you remain on your current branch after its execution. Branches are fundamental for parallel development, allowing teams to work on features or bug fixes independently without interfering with the main codebase.
* git checkout <branch-name>
   * Meaning: Switches your working directory and the HEAD pointer to the specified branch. This effectively changes the files in your working directory to match the state of the project at the tip of that branch. It can also be used for more advanced operations like checking out specific files from other branches or restoring files to a previous state.
* git switch <branch-name>
   * Meaning: A newer, more focused, and generally safer command introduced in Git 2.23 specifically for switching branches. It's designed to prevent accidental "detached HEAD" states when switching to a branch that exists locally. It makes the intent clearer compared to the multi-purpose git checkout.
* git checkout -b <new-branch-name>
   * Meaning: A common shortcut that combines two operations: creating a new branch and immediately switching to it. This is very useful when starting work on a new feature or bug fix.
* git switch -c <new-branch-name>
   * Meaning: Similar to git checkout -b, this is the git switch equivalent for creating a new branch and switching to it in one command.
* git merge <source-branch>
   * Meaning: Integrates changes from the specified <source-branch> into your currently active branch. Git attempts to combine the histories of the two branches. If successful, it typically creates a new "merge commit" that has two parent commits (the tips of the merged branches), explicitly recording the merge event in the history. In some cases (e.g., a linear history), Git might perform a "fast-forward" merge without creating a new merge commit.
* git rebase <target-branch>
   * Meaning: Rewrites commit history by moving your branch's commits to a new base. Instead of creating a merge commit, rebase takes the commits from your current branch and reapplies them one by one on top of the <target-branch>'s latest commit, creating a linear history.
   * Purpose: Often used to maintain a clean, linear, and easy-to-read project history, avoiding "merge commits" and making the history appear as if development happened sequentially. It's frequently used before merging a feature branch into main.
   * Caution: Never rebase commits that have already been pushed to a shared remote repository and that others might have pulled. Rebasing rewrites the history of those commits (they get new hashes), which can cause significant confusion and issues for collaborators who have based their work on the old history. Only rebase local, unpushed commits.
* git branch -d <branch-name>
   * Meaning: Deletes the specified local branch. Git will only allow deletion if the branch has been fully merged into its upstream branch (or HEAD). Use the uppercase -D flag (git branch -D <branch-name>) to force deletion of a branch, even if it contains unmerged changes.
Conflict Resolution
* Merge Conflicts:
   * Meaning: A common scenario in collaborative development where Git cannot automatically combine changes from two different branches. This happens when the same lines of code (or nearby lines) were modified differently in both branches (e.g., you changed line 10, and a colleague changed line 10 in their branch). Git pauses the merge/rebase process and asks for manual intervention because it doesn't know which version to keep.
   * Resolution Process:
      1. When a conflict occurs, Git will mark the conflicting sections in the affected files with special markers (e.g., <<<<<<< HEAD, =======, >>>>>>> branch-name). These markers delineate the different versions of the conflicting code.
      2. You must then manually open and edit the conflicted files using a text editor. You'll review the conflicting sections and decide which changes to keep, combining them as necessary, and removing the Git markers.
      3. After manually resolving the conflicts in all affected files, you use git add <conflicted_file> for each file to inform Git that the conflict in that file has been resolved and the file is ready to be committed.
      4. Finally, you complete the merge by running git commit (if it was a merge) or git rebase --continue (if it was a rebase).
Collaboration Concepts
* Pull Request (PR) / Merge Request (MR)
   * Meaning: A powerful feature provided by Git hosting platforms (like GitHub, GitLab, Bitbucket) that facilitates collaborative development. A Pull Request (GitHub terminology) or Merge Request (GitLab terminology) is a formal proposal to merge changes from one branch (e.g., a feature branch you've been working on) into another branch (e.g., the main or develop branch).
   * Purpose: PRs/MRs serve as a central mechanism for:
      * Code Review: Team members can review the proposed changes, suggest improvements, and catch bugs before they are integrated.
      * Discussion: Comments and discussions can happen directly on the code changes.
      * Automated Checks (CI/CD): Continuous Integration/Continuous Delivery pipelines often trigger automatically on PRs to run tests, linting, and build checks, ensuring code quality and preventing regressions.
      * Visibility: Provides a clear audit trail of changes and approvals.
   * Workflow:
      1. A developer creates a new feature branch from main, makes changes, commits them, and pushes the feature branch to the remote repository.
      2. The developer then navigates to the Git hosting platform (e.g., GitHub) and opens a Pull Request, specifying the source (feature) branch and the target (main) branch.
      3. Team members review the code, provide feedback, and automated tests run.
      4. Once all checks pass and the changes are approved, the Pull Request is merged into the target branch, integrating the new code.
Other Important Concepts
* HEAD
   * Meaning: A symbolic reference that points to the tip of the current branch you are working on. It indicates your current position in the repository's history. Most of the time, HEAD points to a branch name (e.g., HEAD -> main), meaning your current work is associated with that branch.
   * Detached HEAD: If HEAD points directly to a specific commit hash (e.g., git checkout a1b2c3d) instead of a branch name, you are in a "detached HEAD" state. While you can make commits in this state, those commits won't belong to any branch. It's generally advised to create a new branch from a detached HEAD if you intend to continue development from that point.
* origin
   * Meaning: The conventional name given to your primary remote Git repository (e.g., the repository on GitHub that you cloned from or pushed to). While you can name remotes anything you want, origin is the widely accepted default for the main upstream remote.
* master / main
   * Meaning: The common name for the default or primary development branch in a Git repository. Historically, master was the standard. In recent years, main has become the preferred and increasingly common default branch name for new repositories to promote inclusivity. This branch typically represents the stable or production-ready version of the codebase.
* .gitkeep
   * Meaning: A common convention (not a Git command) for a placeholder file. Since Git only tracks files and not empty directories, if you need to ensure an empty directory is part of your repository's structure (e.g., for logs or uploads), you can create an empty file named .gitkeep inside it (e.g., touch my_empty_folder/.gitkeep). You then git add and git commit this .gitkeep file, which forces Git to track the directory.
